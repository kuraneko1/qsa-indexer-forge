# 公開版 indexer から v2 まで：128k の取り違えを直した研究（2026-11-08〜20）

公開版の indexer（v1、MM2 16k）は、128k の文脈で、似た記録を取り違える誤りが多かった。このページは、その弱点を見つけてから、2 段階の追加学習で直し、v2 として公開し直すまでの記録である。

- **期間：** 2026-11-08 に始め、11-19 に研究を終え、11-20 に v2 を公開した。時刻はすべて日本時間（JST）。
- **2 段目の学習（64k）の詳細：** [取り違え重点の 64k 追加学習](training-64k-mixup.md) にある。このページは、その前後（弱点の発見、1 段目の学習、学習なしの重み編集、検証用データでの最終評価、公開）をまとめる。
- **出典：** 研究記録（評価のログ、設定、生データ、課金の記録）からまとめ直し、数字は元のログと照合した。
- **コード：** 1 段目・2 段目の学習コード、設定、学習データの生成器は、2026-11-20 にこの repo に入れた（[8 章](#8-この-repo-に入れたもの)、手順は [indexer v2 の学習を再現する](training-v2.md)）。

## 0. 要旨

rg-V 128k の 240 問（学習にも設定の決定にも使っていない検証用データ）、K=2,048 での正解数：

| indexer | thinking off | thinking low |
|---|---:|---:|
| v1（公開版、MM2 16k） | 169（70.4%） | 185（77.1%） |
| 300b（v2 の 1 段目、公開していない） | 191（79.6%） | 211（87.9%） |
| **v2（mix64k、公開版）** | **215（89.6%）** | **218（90.8%）** |
| dense（indexer を使わず全部見る） | 227（94.6%） | 232（96.7%） |

v1 からの改善：

| 指標 | thinking off | thinking low |
|---|---:|---:|
| 正解数 | +46 問（+27.2%） | +33 問（+17.8%） |
| 正答率 | +19.2 ポイント | +13.8 ポイント |
| 誤答数 | 71 → 25（64.8% 減） | 55 → 22（60.0% 減） |
| v1 と dense の差のうち埋めた割合 | 79.3%（58 問のうち 46 問） | 70.2%（47 問のうち 33 問） |

- **伸び：** v2 は v1 より、off で 27.2%、low で 17.8% 多く正解した。誤答は 6 割以上減り、v1 から dense までの差の約 8 割（off）と約 7 割（low）を埋めた。
- **残る差：** dense との差は、まだ有意に残っている（off p=0.029、low p=0.009）。
- **効いたのは学習：** 学習なしの重み編集は、再生の指標（NLL・capture）では大きく改善した。しかし、課題の正答率は安定して上がらなかった。
- **公開：** 2026-11-20 に、BF16 と GGUF の公開 repo の indexer を v2 に差し替えた。v1 は、Hugging Face のタグ `v1` で取れる。

## 2. 最終の比較：rg-V 128k

### 2.1 測り方

- **データ（rg-V）：**
  - recall-grid の生成器で作った 240 問（8 種類 × 10 深さ × 3）。seed は 20261202。
  - 本文は、PG-19 の validation・test の本 49 冊。128k は 2 文書（約 127.1k token）。
  - 学習にも、学習の設定を決めるのにも使っていない。データの分け方は 6.4 にある。
- **モデル：**
  - 公開 GGUF の Q8_0（v1、HF commit `e4c378e`）に、indexer の 80 テンソルだけを書き込んだ。
  - indexer は F32 のまま書くので、量子化は起きない。ほかのテンソルとメタデータは、どの indexer でも同じ。
- **エンジン：**
  - [pentaCoxian/Qwen-QSA-llama.cpp](https://github.com/pentaCoxian/Qwen-QSA-llama.cpp) の `70b4e14`（llama.cpp の base は、この repo の patch と同じ `6209237`）を、sm_80 でビルドした。
  - Modal の A100 80GB 1 枚で動かした。
  - このエンジンは、[来歴](provenance.md) で「IQ3_S 派生」と呼んでいるものである。本流のエンジン（[kuraneko1/Qwen3.8-27B-QSA-llama.cpp](https://github.com/kuraneko1/Qwen3.8-27B-QSA-llama.cpp) の `864934c`）とは、コードの 15 ファイル（GDN の MMA カーネル、KV キャッシュ、server など）が違う。
  - 研究中に手元の評価機で使ったエンジンも、ソースの tree が同じ（`efdc7d2`）である。v2 を本流のエンジンで動かした確認は、まだない（13 章）。
- **設定：** context 262,144、FP16 KV、MTP draft 2、K=2,048、greedy、出力の上限 65,536 token。
- **thinking：**
  - off は、推論のブロックなしで答える。
  - low は、chat template の `reasoning_effort: "low"`。
- **dense：** 環境変数 `LLAMA_QSA_DENSE` を設定し、16 層を通常の注意に戻したもの。この変数は値が何であれ、設定されているだけで dense になる。
- **経路の確認：** どの回も、起動ログの `QSA27B route:` で経路を確かめた（sparse の回は `sparse text`）。
- **繰り返しの打ち切り：**
  - v1 の 2 本だけ、明らかなループを打ち切る仕組みが入っている。出力の末尾 12,000 文字の zlib 圧縮率が 0.05 を下回ったら止める。
  - 止めたのは off で 5 問、low で 1 問で、どれも不正解の流れだった。
  - ほかの 8 本は、この仕組みを入れる前に測った。

## 3. 弱点の発見（11-08）

- **比べ方：** 同じ重み・同じエンジンで、indexer の ON と OFF（dense）だけを変えた。
- **落ちなかったもの：** 単純な検索（RULER など）は、180k でも落ちなかった。
- **大きく落ちたもの：** recall-grid 128k だけだった（このときは旧 240 問で、本文は Python の標準ライブラリ）。
  - dense 227/240 に対して、QSA（ship）は 163/240。
  - K=4,096 にすると 204。
- **落ちる条件：** 落ちるのは、文書の深さではなかった。**似た記録を取り違えるとき**と、**記録をたどる連鎖**のときだった。
- **原因の見立て：**
  - 128k では、選ぶ候補が 32,768 ブロックになる。K=2,048（512 ブロック）では、その 1.56% しか見られない。
  - 学習時の 16k では 12.5% だったので、8 倍の差がある。
- **16k の代わりの試験（プロキシ）：**
  - 16k で K=256（同じ 1.56%）にすると、同じ失敗が再現した。
  - そこで、16k の 81 問を、安く試せるプロキシにした。プロキシでの正解は、ship 44、v1 45、dense 78。

## 4. 1 段目：300b（11-09、Modal）

狭い予算でも正解を上位に置けるように、教師（dense の注意）との KL に 2 つの項を足して、v1 から 300 step 追加学習した。

### 4.1 設定

| 項目 | 値 |
|---|---|
| 初期値 | v1（BF16 repo の `indexers/qsa_indexers.pt`、sha256 `e44193e5…`） |
| 系列長・予算 | 16,384 token、K=2,048（512 ブロック = 12.5%） |
| step | 300（1 step = 1 系列）、合計 4,915,200 token |
| 最適化 | AdamW（β 0.9, 0.95）、lr 5e-5、勾配の上限 1.0、seed 0 |
| 損失 | KL（教師のブロック分布、全ブロック・全位置）＋ λ·(1 − 問題文の token での正解ブロックの質量) ＋ μ·relu(margin − (s_正解 − s_偽物)) |
| 係数 | λ=0.3、μ=0.1、margin=2.0 |
| 計算 | Modal A100 80GB、1 step 約 15 秒、約 75 分 |
| 結果 | `qsa_indexers.pt`（sha256 `5b760e46…`） |

### 4.2 データ

| 項目 | 値 |
|---|---|
| 生成器 | recall-grid の生成器（`make_item`・`Keys`・`load_filler`）を使った学習用の生成器 |
| 本文（記録の間を埋める文章） | Python の標準ライブラリのソース（旧 240 問の評価と同じ） |
| seed | 1001（評価の seed とは別） |
| 規模 | 600 問 = 200 文書 × 3 問。1 問が 16,384 token の 1 系列。記録の密度 0.6（128k の 0.15 と同じ混み具合を 16k で再現） |
| ラベル | `answer_pos`：答えに要る記録の**先頭の token** の位置（1 問あたり中央値 3）。`decoy_pos`：偽物の記録の位置（600 問中 463 問） |
| 混ぜた一般の文章 | FineWeb-Edu（sample-10BT、revision `87f09149…`） |

- **配分の訂正（あとで分かったこと）：**
  - 設定上は「合成 70%＋FineWeb 30%」だった。しかし、混ぜ方の関数 `combine_iterators` は `(n % 10) <= 7` で合成を選ぶので、10 本中 8 本が合成になる。
  - 実際の配分は、**合成 240 step＋FineWeb 60 step（80% と 20%）**だった。学習ログでも、step 8・9・18・19・… の 60 step だけ、正解の指標が 0 になっている。
- **実際に使った問題：**
  - 合成のデータは、シャッフルせずに先頭から順に読む。使ったのは先頭の約 240 問で、600 問のうち約 360 問は使っていない。
  - 種類ごとの数は、code 36、quantities 36、ingredients 35、revision 30、join 28、pointer 28、guid 24、binding 23。
- **学習の推移（合成の step だけで集計）：**

  | step | loss | answer_recall@512 |
  |---|---:|---:|
  | 1〜50 | 0.886 | 0.676 |
  | 51〜150 | 0.879 | 0.622 |
  | 151〜250 | 0.851 | 0.625 |
  | 251〜300 | 0.848 | 0.542 |

  - FineWeb の step は、loss 0.239、capture 0.940 だった。
  - answer_recall@512 は、学習中に下がっている。λ と μ の項は上位を鋭くするので、12.5% の予算の指標には効果が出ない（4.3）。

### 4.3 結果

- **プロキシ（16k、K=256、81 問）：** ship 44 → 300b 60（p=0.0009）。改善は学習によるもので、学習していない v1 を同じ手順で入れても 45 だった（300b vs v1 は 15 対 0、p=0.0001）。
- **128k の旧 240 問：** 212（ship 163）。K=4,096 では 225 で、dense の 227 と差がない。
- **守りの指標（悪化していないか）：**
  - 分布の外の課題（実コーパスの記憶 246 問）：ship 217 → 300b 218（dense 199）。悪化しなかった。
  - 64k の実文章の PPL（dense 比）：ship +1.96% → 300b +1.75%。
- **測り方の失敗：**
  - HF 側の recall@512（予算 12.5%）では、「改善なし」に見えた。
  - 運用と同じ 1.56% で測り直して、初めて改善が見えた。評価は、運用と同じ予算の比で行う必要がある。
- **旧 240 問の限界：** 旧 240 問は 300b の学習データと同じ生成器・同じ本文なので、300b にとっては独立した試験ではない。そこで 11-15 に、本文を PG-19 にした新しいデータ（6.4）を作った。

### 4.4 研究中に見つけた不具合（研究用の写しで修正済み）

- **パッチが呼ばれない：** accelerate のフックが、差し替える前の forward を持っていた。そのため QSA のパッチが呼ばれず、学習が空回りしていた。
- **NaN：** 選んだブロックの中で教師を正規化し直す KL（論文の式 20）で、有効なブロックが足りない行に −inf が入り、NaN になっていた。

## 5. 学習なしの重み編集（11-14〜17、11-19）

300b の学習による重みの変化を調べると、ランクが低かった（512 次元のうち約 50）。また、64 head のうち 14 が「死んだ head」だった。ReLU の手前が常に負で、勾配が 0 になるため、学習では動かない。そこで、学習せずに重みを直接編集する道を試した。

| 日付 | 編集 | 選び方 | 課題での結果 | 判定 |
|---|---|---|---|---|
| 11-14 | **E1：変化量の伸縮** v1 + α(300b − v1)、α = 0.5・1.5・2 | 事前に決めた規則（16k プロキシ） | 対照 58、α1.5 63（7 対 2、p=0.18）、α2 64（1 文字違いの識別が崩れ始める）、α0.5 52 | α1.5 を採用（プロキシのみ） |
| 11-14 | **E2：低ランク化**（変化量の上位 8・32・64 成分） | 同上 | 57・55・57（雑音の範囲） | 改善の大半は上位約 8 成分に収まる |
| 11-15 | **層ごとのチェックポイント選択**（層 3・7 は ship、ほかは α1.5） | 128k の再生での capture | 64k 以上で α1.5 を上回る（capture） | best に採用 |
| 11-15 | **死んだ head の符号反転**（3:0、3:1、7:0、15:0、23:0、35:2、55:2） | 同上（層ごと） | 128k で層 3 の取りこぼしの 57% が戻る。16k〜32k では逆効果 | best に採用 |

| 11-15 | 生きた head を死んだ head に複製 | 同上 | −4% | 不採用 |
| 11-15 | **best**（層ごとの選択 ＋ 上の 13 個の編集） | 再生の NLL・capture | 128k の超過 NLL 0.0180 → 0.0074。rg-E 207（300b 205、p=0.87）。rg-V（A100）は off 207（300b 191、p=0.026）、low 217（300b 211、p=0.28） | 課題では安定しない |
| 11-16 | **答えを上げる編集**（閉じた形の ridge で低ランクの ΔW_q、層 23・27・31・35・55） | 模擬器（エンジンと 1e-5 で一致） | 模擬器で答え +0.035、偽物も +0.018 上がる | GGUF にはしていない |

| 11-19 | **mbops**（mix64k ＋ best の 13 個の編集） | rg-E（事前の規則） | 211（mix64k 213、p=0.83） | 効果なし |
| 11-19 | **mba15**（best の作り方で、300b を mix64k に置き換え） | 同上 | 208（mix64k 213、p=0.38） | 効果なし |

  - 死んだ head の反転と RoPE 側の利得は、「近くの位置」より「遠くの内容」を重くする編集で、長い文脈の取りこぼしを減らす。
  - 一方で、取り違えのような細かい識別は直らなかった。
- **線形の編集の限界：** 探索用のデータ（E）で合わせた W_q の線形の編集は、検証用のデータ（V）では理想の約 0.27 しか効果が出なかった。文書をまたいで汎化しない。
- **決め手（11-17）：** 300b を、best と同じ rg-E で測った。300b 205 に対して best 207（p=0.87）で、best の編集は課題の正答率を上げていなかった。revision の問題では、むしろ悪化していた（17 対 23）。
- **mix64k に載せた編集（11-19）：** 取り違えは減ったが、材料の組の誤りと「null を値で答える」誤りが同じくらい増え、合計は変わらなかった。事前の規則どおり、V には進めなかった。

## 6. 弱点の特定から 2 段目へ（11-16〜18）

### 6.1 取り違えが主な誤り

- **内訳：** rg-E の 300b の誤り 35 問のうち、26 問が取り違えだった（1 文字違いの偽物 11、別の記録の値 11、null の取り違え 4）。
- **検索の失敗ではなかった：** revision の誤りでは、正しい記録は出力の中に引用されていた。そのうえで、1 文字違いの別の項目の新しい版を、同じ項目と読み違えていた。
- **記録が部分的にしか選ばれない：**
  - 1 つの記録は、複数のブロックにまたがる。
  - 偽物の値の側のブロックだけが選ばれ、キーの側が選ばれないと、モデルは 1 文字の違いを確かめられない。
  - best だけが誤る問題では、どの層でも選ばれていない正解ブロックが 57% あった。
- **q を線形に強める編集では直らない：** 1 文字違いの偽物は、正解と同じ方向に順位が動く。編集で正解を上げると、偽物も一緒に上がった（5 章）。

### 6.2 1 段目の学習の穴

- **ラベルが記録の一部だけ：** 偽物との差の項はあったが、ラベルは記録の**先頭の token** だけだった（中央値 3 位置）。
- **系列の長さ：** 学習は 16k だけで、運用の 128k より 8 倍短かった。

### 6.3 2 段目：mix64k

2 段目では、6.2 の 2 点を直して、300b から 64k で 300 step 追加学習した。詳細は [取り違え重点の 64k 追加学習](training-64k-mixup.md) にある。

| 項目 | 300b（1 段目） | mix64k（2 段目） |
|---|---|---|
| 初期値 | v1 | 300b |
| 系列長 | 16,384 | **65,536** |
| step | 300 | 300 |
| μ（偽物との差）・margin | 0.1・2.0 | **0.3**・2.0 |
| ラベル | 記録の先頭の token | **記録の全 token**（正解・偽物とも） |
| KL | 全ブロック | **選んだ上位 512 ブロックの中で、教師を正規化し直す**（論文の式 20） |
| KL を取る位置 | 全位置 | 問題文の全 token と、step ごとにランダムな 4,096 の文書位置 |
| データ | 合成 80%＋FineWeb 20%、本文は Python | 合成 100%（300 問、各問題を 1 回だけ）、本文は PG-19 の **train** の本 |
| 種類の配分 | ほぼ均等 | pointer 86、revision 71、code 41、guid 31、ingredients 20、binding 19、join 16、quantities 16 |
| 計算 | Modal A100、約 75 分 | Colab A100 80GB、5.26 時間（63.1 秒/step、メモリの山 78.7 GB） |

- **重みの変化：** 300b からの変化は、相対的な Frobenius ノルムで、q_proj・k_proj とも 6.1% だった。
- **動いた head：** 300b ではほとんど動かなかった head の一部（層 11 の h1・h3、層 19 の h1・h3 など）が、2〜8% 動いた。best で反転した 7 個の死んだ head は、mix64k でもほとんど動かなかった（変化 0.3% 以下、層 55 の h2 だけ 3%）。
- **rg-E（評価機、off）：** 212（300b 205、best 207、dense 223）。

### 6.4 探索・検証・最終のデータを分けた（rg-v3）

11-15 に、本文を PG-19 にした新しいデータを作り、使い道を分けた。同じ生成器（8 種類 × 10 深さ × 3）で、長さは 16k・32k・64k・128k・192k。

| データ | 用途 | seed | 本文（PG-19 の本） |
|---|---|---|---|
| rg-E | 探索（編集の選択や、学習の種類の重みを決めるのに使ってよい） | 20261201 | 41 冊 |
| rg-V | 検証（候補の絞り込み、最終の比較） | 20261202 | 49 冊 |
| rg-F1・F2 | 最終（封印。1 回だけ使う） | 20261203・20261204 | 各 30 冊 |

- **本の分け方：** PG-19 の test 100 冊と validation 50 冊を、題名の sha256 で振り分けた。同じ本が 2 つの分割に入ることはない。
- **学習データとの関係：** mix64k の学習データは PG-19 の train の本から作ったので、E・V・F とは題名が 1 つも重ならない。E から借りたのは、種類の重みを決めるための誤りの内訳だけである。
- **F は使っていない：** v2 の公開までに、F は使っていない。

## 12. 分かったこと

1. **評価は、運用と同じ予算の比で行う。** 12.5% の指標では、300b の改善が見えなかった。
2. **比べるのは、同じ環境・同じ設定の中だけ。** GPU が変わると同じ重みで 13 問が入れ替わり、同じ環境の再実行でも 6/240 が入れ替わる。
3. **選択に使ったデータで、改善を判断しない。** best は再生の指標では大きく良くなったが、課題では安定しなかった。探索（E）・検証（V）・最終（F）を分けたことで、それが見えた。
4. **候補を積み上げる前に、親と同じ問題で比べる。** best と 300b を同じ課題で比べたのは 11-17 で、もっと早くやるべきだった。
5. **`LLAMA_QSA_DENSE` は、値が何であれ設定されているだけで dense になる。** 起動ログの `QSA27B route: sparse text` を必ず確かめる。
6. **thinking の長い greedy は、繰り返しに入りやすい。** 末尾 12,000 文字の zlib 圧縮率で、明らかなループを打ち切った（4,032 件の出力で校正）。
7. **見張りのスクリプトは、長い本番の前に、本物のログで試す。** mix64k の 1 回目は、見張りの読み違いで止まった。
8. **設定の値と、コードの実際の動きを照合する。** 300b の混ぜ方は、設定の 70/30 ではなく 80/20 だった。
